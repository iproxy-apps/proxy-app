## A. Money model

| # | Decision | Status | Choice | Why |
|---|---|---|---|---|
| D1 | Who pays the fees | **SETTLED (owner, 2026-11-23)** | Client pays exactly `offeredPrice` (the number they typed): `chargedAmount = offeredPrice`. Proxy receives `proxyEarnings = offeredPrice × 0.80`. Platform keeps `platformFee = offeredPrice × 0.20` and pays Stripe's fee (`3.99 % of the charge + R$ 0,39`) out of it (`platformNet = platformFee − stripeFee`, bookkeeping only). Example R$ 100: client pays R$ 100, proxy gets R$ 80, Stripe R$ 4,38, platform nets R$ 15,62. Bounds: `MIN_OFFERED_PRICE = 20` (below that the fixed fee eats the margin), `MAX_OFFERED_PRICE = 10000`. All math in `Prisma.Decimal`, ROUND_HALF_UP to 2 places (D2). | Owner leaned "proxy absorbs everything" (as coded today); Claude recommended 80/20 with the Stripe fee on the platform (Uber/99 model): one number for each side, no odd cents on the proxy side, Stripe is the platform's cost. Supersedes `SPEC.md §8.8` and the app `PriceBreakdown` (client sees no fee lines; proxy sees "Você recebe" = 80 %). |
| D2 | Fee math | SETTLED | All money math in `Prisma.Decimal`, 2 dp, centavos as `Decimal.mul(100).toDecimalPlaces(0).toNumber()`. Single source of truth `src/common/money.ts` in proxy-api, exposed to the app via `GET /tasks/:id` fields (`offeredPrice`, `platformFee`, `stripeFee`, `chargedAmount`, `proxyEarnings`). App never recomputes fees; it renders backend numbers. | BE-03, BE-39, APP-04. |
| D3 | Card charging / 3DS | **SETTLED (owner, 2026-11-23)** | Keep the separate-charges-and-transfers architecture already in the code. Card saved through a **SetupIntent** (`usage: 'off_session'`, confirmed on the client's device, 3DS once at save). `/tasks/start` **claims first** (CAS `available → in_progress` + executor mapping, so a losing proxy never reaches Stripe), then creates **and confirms** a PaymentIntent for `offeredPrice` with `off_session: true`, **automatic capture**, idempotency key `start:<taskId>:<proxyId>:<startedAt ms>` (Stripe keeps a declined result under a key for 24 h, so the suffix lets the same proxy retry); `succeeded` → payment row; definite failure → release the claim; unknown outcome (`processing`, network) → keep the claim, 409 `PAYMENT_PENDING`, settled by webhooks/retry. Funds sit in the platform balance. `/tasks/validate` (or the 7-day auto-release, D18) transfers `proxyEarnings` with `source_transaction = chargeId`. `/tasks/cancel` refunds in full (D7). Payment state is also written from webhooks (idempotent). Any definite non-`succeeded` outcome (incl. `requires_action`): claim released, task back to `available`, the proxy gets a 409 "Não foi possível cobrar o cliente" and the client is notified "Confirme seu cartão na Carteira" (re-save the card). No manual capture anywhere. | The 2026-11-08 default (manual-capture hold at start, capture at validate) was dropped on Claude's recommendation: card authorisations expire after 7 days and task duration + the 7-day validation window (D18) exceeds that. Charge-at-start costs the Stripe fee on cancellations, already accepted in D7. |
| D4 | Pending BRL funds | SETTLED | Persist `Payments.chargeId` from `latest_charge`; `transfers.create({ source_transaction: chargeId, transfer_group: taskId }, { idempotencyKey })`. | BE-08. Needs one Stripe test-mode verification (see `QA-CHECKLIST.md`). |
| D5 | `payout.failed` policy | **SETTLED (owner, 2026-11-23)** | Notification only: log, set `Users.payoutIssue = true`, surface "Atualize seus dados bancários na Carteira" + push. No reversal, no `payout_failed` task status (enum value kept for existing rows, never written again). Stripe returns the funds to the proxy's balance and retries the payout by itself once the bank data is fixed; `account.updated` clears the flag. | BE-24: the current claw-back cannot even match the event shape. Owner confirmed. |
| D6 | Chargebacks after validation | **SETTLED (owner, 2026-11-23)** | Persist `Payments.disputeId`, set payment `disputed`, block `finish`/`validate`/`cancel` on disputed payments, do **not** auto-reverse the transfer and do **not** debit `walletBalance` ("Total recebido", D8). The owner answers the dispute in the Stripe dashboard with the proof photo + the client's validation timestamp; if lost, the platform absorbs it in 1.0. Charging the proxy back is a terms-of-use item for a later version. | BE-25. Owner confirmed. |
| D7 | Cancellation after charge | **SETTLED (owner, 2026-11-23)** | Client cancel while `in_progress` (≤ 1 h after `startedAt`) refunds the **full charged amount**; platform absorbs Stripe's non-refundable fee for 1.0. | Owner: fair, the client should not lose money for creating a task. Revisit with volume. |
| D8 | What "Saldo" means | **SETTLED (owner, 2026-11-23)** | Rename to "Total recebido" (running total of `proxyEarnings` credited). Stripe connected balance is out of scope for 1.0. | NEW-06. |

## B. Accounts & sessions

| # | Decision | Status | Choice | Why |
|---|---|---|---|---|
| D9 | Session lifetime | **SETTLED (owner, 2026-11-23)** | Access JWT `expiresIn: '30m'` + opaque **refresh token** (32 random bytes, stored as a SHA-256 hash in a `RefreshTokens` table: `userId`, `expiresAt` = 60 days, `revokedAt`, `replacedById`), rotated on every use; reuse of a rotated token revokes the whole family. `POST /auth/refresh` with the refresh token → new pair; `POST /auth/logout` revokes. Password reset/change and account deletion revoke all the user's refresh tokens. App: axios interceptor on **401** runs a single-flight refresh, retries the original request once, signs out when the refresh fails. Replaces the 30-day JWT + `tokenVersion` default. | Owner proposed short access token + silent refresh; revocable and standard. BE-13, APP-05. |
| D10 | Money/stats in the JWT | SETTLED | Signed as numbers (`.toNumber()`), app normalises with Zod on decode. New `GET /auth/me` returns the fresh user subset; the token keeps the claims for backwards compatibility. | BE-16, APP-11. |
| D11 | `userType` switching | SETTLED | Not in 1.0 (SPEC §8.14). Removed from `update-profile`; choose-profile copy changed. | BE-14. |
| D12 | Document photo + CPF/CNPJ | **SETTLED (owner, 2026-11-23)** | Proxy does **not** collect or store identity documents at all: sign-up drops document type/number/photo; the proxy's CPF/ID is collected by Stripe during Connect onboarding and stays there. `documentType`/`documentUrl`/`isVerified` are dropped by the Phase 2 migration; "Verificado" badge removed. | Owner first wanted the document kept encrypted so nobody could read it; data nobody can read has no use, and not holding it is the strongest LGPD position. Stripe already does the KYC. APP-06, Q12, Apple 2.3.1. |
| D13 | Account deletion with open listings | SETTLED | `available` tasks the user owns are auto-cancelled in the same transaction; deletion blocks only on `in_progress`/`verification_required` (as owner or executor). Cards soft-deleted + PaymentMethods detached; Stripe Customer PII scrubbed; ids kept 180 days. | BE-17, BE-30, REL-04. |
| D14 | Edit profile | **SETTLED (owner, 2026-11-23)** | In 1.0: the existing `update-profile` route (hardened in P2-T06) edits `name` and `phone` only; e-mail and password changes stay out (password via forgot-password). App keeps "Editar dados" → an edit screen (Phase 3). Account deletion ships (D13, store requirement). | Owner: small work, and deletion is required by the stores. Reverses the 2026-11-08 default. |
| D15 | Rating on validate | SETTLED | Optional (SPEC + backend). The UI must not force it. | F2-24. |

- Finish has no 1 h limit (commit `d20bae9`); SPEC §7.2 updated in Phase 2 docs task.

- `targetSdkVersion` is 36 with Expo SDK 57; nothing to do for Play's 2026 target.
- Required iOS purpose strings: location when-in-use, camera, photo library. Always-location and microphone must be disabled in the plugin config (`false`), not deleted.
- Stripe Connect accounts already use controller properties (not the deprecated `type: 'express'`); only `country: 'BR'`, `default_currency: 'brl'` and `capabilities.transfers` are missing.
